## 1. Problem

Every feature that moves money (settlement, splits, holds, payouts, refunds) must record that movement in one place that cannot lie. The record must stay correct when the same request arrives twice, when a hundred requests hit the same balance at once, when a transaction fails halfway, and when someone with database access tries to change history.

The platform overview fixes the principles: double-entry, immutable entries, derived balances and seven invariants (I1–I7). This document decides how the `ledger` module implements them.

## 2. Goals and non-goals

**Goals**

- Every money movement is one balanced entry, posted atomically with the business change that caused it.
- Each invariant is enforced by at least one mechanism the application cannot bypass, and checked again by an independent verifier.
- Concurrent postings never overdraw a guarded balance and never deadlock.
- Posting the same source fact twice has one effect.

**Non-goals**

- Multi-currency conversion. Entries balance per currency; phase 1 uses only `BRL`.
- General accounting (closing periods, financial statements, tax). The ledger records what the platform owes and holds.
- A public HTTP API. Modules call the ledger in-process; the console reads it through module APIs.
- Event sourcing (overview, section 8).

## 3. Model

### 3.1 Concepts

| Concept | Meaning |
|---|---|
| **Account** | A named bucket of money in one currency, owned by a tenant, such as `tenant:{id}:available`. Its type (asset, liability, revenue, expense) fixes its normal balance. Accounts are configuration: created once, never changed |
| **Entry** | One money movement: two or more postings whose debits equal their credits, per currency. It records the source fact that caused it |
| **Posting** | One leg of an entry: an account, a direction (debit or credit) and a positive amount |
| **Balance** | The sum of an account's postings, in the direction of its normal balance. A projection of the postings, kept up to date for fast reads and for the overdraft check |
| **Hold** | Money reserved for a pending operation, such as a payout. A hold is an entry from `…:available` to `…:held`; releasing it is another entry. There is no separate holds table |
| **Reversal** | An entry that undoes another, with the original's postings in the opposite direction and a link to it. Mistakes are corrected only this way |

### 3.2 Signs

Amounts are always positive; the direction carries the sign. An account's balance grows with postings in its normal direction and shrinks with the others:

| Type | Normal balance | A debit | A credit |
|---|---|---|---|
| Asset, expense | Debit | increases it | decreases it |
| Liability, revenue | Credit | decreases it | increases it |

So in the settlement example of the overview (section 6.4), the debit of R$ 100.00 to `platform:settlement` raises that asset by 100.00, and the credits raise the three liability and revenue accounts by 70.00, 27.00 and 3.00.

### 3.3 Schema

All tables live in the `ledger` schema, owned by the migration role. Timestamps are `timestamptz`, money is `bigint` minor units, enumerations are `text` with a `CHECK`.

```
accounts
  id              uuid primary key (UUIDv7)
  tenant_id       uuid not null
  code            text not null                      -- e.g. tenant:{id}:available
  type            text not null                      -- ASSET | LIABILITY | REVENUE | EXPENSE
  normal_balance  text not null                      -- DEBIT | CREDIT, consistent with type
  currency        char(3) not null
  allow_negative  boolean not null
  is_hot          boolean not null
  created_at      timestamptz not null
  unique (tenant_id, code)
  unique (id, tenant_id, currency)                   -- target of the postings foreign key
  check (not is_hot or allow_negative)               -- see section 5.3

entries
  id                 uuid primary key
  tenant_id          uuid not null                   -- tenant of the source fact
  source_type        text not null                   -- e.g. charge, payout, refund
  source_id          text not null                   -- the fact's ID, at most 64 characters
  purpose            text not null                   -- e.g. settlement, payout_hold
  effective_date     date not null                   -- business date in America/Sao_Paulo
  reverses_entry_id  uuid null references entries
  correlation_id     text not null
  created_at         timestamptz not null
  unique (source_type, source_id, purpose)

postings
  id          uuid primary key
  entry_id    uuid not null references entries
  account_id  uuid not null
  tenant_id   uuid not null                          -- the account's tenant, for Row-Level Security
  currency    char(3) not null
  direction   text not null                          -- D | C
  amount      bigint not null check (amount > 0)
  created_at  timestamptz not null
  foreign key (account_id, tenant_id, currency) references accounts (id, tenant_id, currency)
  index (entry_id), index (account_id, id)

balances
  account_id    uuid primary key references accounts
  balance       bigint not null
  version       bigint not null                      -- incremented on every change
  folded_until  timestamptz null                     -- hot accounts only, see section 5.3
  updated_at    timestamptz not null
```

The composite foreign key on `postings` makes the database reject a posting whose currency or tenant differs from its account's. A balance row is created with its account, at zero, in the same transaction.

**Platform accounts** (`platform:settlement`, `platform:fees`) belong to a reserved platform tenant. An entry belongs to the tenant of its source fact, while each posting carries the tenant of its account, so a tenant's Row-Level Security policy shows the postings to its own accounts and never the platform's.

`created_at` on entries and postings is the database's transaction time (`now()`), not the application clock: the hot-account folding in section 5.3 relies on the database clock alone. Business time is `effective_date`, from the injected `Clock` through `BusinessCalendar`.

### 3.4 Refinements of the overview

This document adds to section 6 of the overview without changing its principles:

| Overview | This design | Reason |
|---|---|---|
| `postings` without tenant or time | `tenant_id` and `created_at` on postings | Row-Level Security per account owner; hot-account folding |
| Refund "referencing the original" | `entries.reverses_entry_id` | The link is a column, checked by a foreign key |
| `balances` | Adds `folded_until` | Hot-account folding |
| `EntryId post(EntryRequest)` | `PostResult post(EntryRequest)`, a sealed result | Insufficient funds is an expected outcome, modeled as a value (overview, section 19.1) |
| — | `openAccount` in the API | Accounts must be created before postings reference them |
