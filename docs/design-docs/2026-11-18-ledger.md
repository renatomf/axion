## 1. Problem

Every feature that moves money (settlement, splits, holds, payouts, refunds) must record that movement in one place that cannot lie. The record must stay correct when the same request arrives twice, when a hundred requests hit the same balance at once, when a transaction fails halfway, and when someone with database access tries to change history.

The platform overview fixes the principles: double-entry, immutable entries, derived balances and seven invariants (I1–I7). This document decides how the `ledger` module implements them.

## 2. Goals and non-goals

**Goals**

- Every money movement is one balanced entry, posted atomically with the business change that caused it.
- Each invariant is enforced by at least one mechanism the application cannot bypass, and checked again by an independent verifier.
- Concurrent postings never overdraw a guarded balance and never deadlock.
- Posting the same source fact twice has one effect.

**Non-goals**

- Multi-currency conversion. Entries balance per currency; phase 1 uses only `BRL`.
- General accounting (closing periods, financial statements, tax). The ledger records what the platform owes and holds.
- A public HTTP API. Modules call the ledger in-process; the console reads it through module APIs.
- Event sourcing (overview, section 8).

## 3. Model

### 3.1 Concepts

| Concept | Meaning |
|---|---|
| **Account** | A named bucket of money in one currency, owned by a tenant, such as `tenant:{id}:available`. Its type (asset, liability, revenue, expense) fixes its normal balance. Accounts are configuration: created once, never changed |
| **Entry** | One money movement: two or more postings whose debits equal their credits, per currency. It records the source fact that caused it |
| **Posting** | One leg of an entry: an account, a direction (debit or credit) and a positive amount |
| **Balance** | The sum of an account's postings, in the direction of its normal balance. A projection of the postings, kept up to date for fast reads and for the overdraft check |
| **Hold** | Money reserved for a pending operation, such as a payout. A hold is an entry from `…:available` to `…:held`; releasing it is another entry. There is no separate holds table |
| **Reversal** | An entry that undoes another, with the original's postings in the opposite direction and a link to it. Mistakes are corrected only this way |

### 3.2 Signs

Amounts are always positive; the direction carries the sign. An account's balance grows with postings in its normal direction and shrinks with the others:

| Type | Normal balance | A debit | A credit |
|---|---|---|---|
| Asset, expense | Debit | increases it | decreases it |
| Liability, revenue | Credit | decreases it | increases it |

So in the settlement example of the overview (section 6.4), the debit of R$ 100.00 to `platform:settlement` raises that asset by 100.00, and the credits raise the three liability and revenue accounts by 70.00, 27.00 and 3.00.

### 3.3 Schema

All tables live in the `ledger` schema, owned by the migration role. Timestamps are `timestamptz`, money is `bigint` minor units, enumerations are `text` with a `CHECK`.

```
accounts
  id              uuid primary key (UUIDv7)
  tenant_id       uuid not null
  code            text not null                      -- e.g. tenant:{id}:available
  type            text not null                      -- ASSET | LIABILITY | REVENUE | EXPENSE
  normal_balance  text not null                      -- DEBIT | CREDIT, consistent with type
  currency        char(3) not null
  allow_negative  boolean not null
  is_hot          boolean not null
  created_at      timestamptz not null
  unique (tenant_id, code)
  unique (id, tenant_id, currency)                   -- target of the postings foreign key
  check (not is_hot or allow_negative)               -- see section 5.3

entries
  id                 uuid primary key
  tenant_id          uuid not null                   -- tenant of the source fact
  source_type        text not null                   -- e.g. charge, payout, refund
  source_id          text not null                   -- the fact's ID, at most 64 characters
  purpose            text not null                   -- e.g. settlement, payout_hold
  effective_date     date not null                   -- business date in America/Sao_Paulo
  reverses_entry_id  uuid null references entries
  correlation_id     text not null
  created_at         timestamptz not null
  unique (source_type, source_id, purpose)

postings
  id          uuid primary key
  entry_id    uuid not null references entries
  account_id  uuid not null
  tenant_id   uuid not null                          -- the account's tenant, for Row-Level Security
  currency    char(3) not null
  direction   text not null                          -- DEBIT | CREDIT
  amount      bigint not null check (amount > 0)
  created_at  timestamptz not null
  foreign key (account_id, tenant_id, currency) references accounts (id, tenant_id, currency)
  index (entry_id), index (account_id, id)

balances
  account_id    uuid primary key references accounts
  balance       bigint not null
  version       bigint not null                      -- incremented on every change
  folded_until  timestamptz null                     -- hot accounts only, see section 5.3
  updated_at    timestamptz not null
```

The composite foreign key on `postings` makes the database reject a posting whose currency or tenant differs from its account's. A balance row is created with its account, at zero, in the same transaction.

**Platform accounts** (`platform:settlement`, `platform:fees`) belong to a reserved platform tenant. An entry belongs to the tenant of its source fact, while each posting carries the tenant of its account, so a tenant's Row-Level Security policy shows the postings to its own accounts and never the platform's.

`created_at` on entries and postings is the database's transaction time (`now()`), not the application clock: the hot-account folding in section 5.3 relies on the database clock alone. Business time is `effective_date`, from the injected `Clock` through `BusinessCalendar`.

### 3.4 Refinements of the overview

This document adds to section 6 of the overview without changing its principles:

| Overview | This design | Reason |
|---|---|---|
| `postings` without tenant or time | `tenant_id` and `created_at` on postings | Row-Level Security per account owner; hot-account folding |
| Refund "referencing the original" | `entries.reverses_entry_id` | The link is a column, checked by a foreign key |
| `balances` | Adds `folded_until` | Hot-account folding |
| `EntryId post(EntryRequest)` | `PostResult post(EntryRequest)`, a sealed result | Insufficient funds is an expected outcome, modeled as a value (overview, section 19.1) |
| — | `openAccount` in the API | Accounts must be created before postings reference them |

## 4. Invariants

Each invariant has a first line of defense that rejects a violation before it is committed, and a second that detects one that got through.

| # | Invariant | Prevented by | Detected by |
|---|---|---|---|
| I1 | Every entry balances per currency, with at least two postings | The `Entry` constructor; a deferred constraint trigger checked at commit | Verifier |
| I2 | Entries and postings are immutable | The ledger role has no `UPDATE`, `DELETE` or `TRUNCATE` on them; a trigger rejects updates and deletes by any role | — |
| I3 | A balance not allowed to go negative never does | The conditional balance update (section 5.2) | Verifier, through I6 |
| I4 | A source fact produces at most one entry per purpose | `unique (source_type, source_id, purpose)` | — |
| I5 | Amounts are positive integers in minor units | `Money` and the `Posting` constructor; `check (amount > 0)` | — |
| I6 | Each balance equals the sum of its account's postings | Balances change only in the transaction that inserts the postings | Verifier |
| I7 | Total debits equal total credits per currency | Follows from I1 | Verifier |

**The deferred trigger (I1).** A constraint trigger `AFTER INSERT ON postings ... DEFERRABLE INITIALLY DEFERRED` runs at commit, when all of an entry's postings exist, and raises an error if the entry's debits and credits differ in any currency. A second one on `entries` rejects an entry with fewer than two postings. Deferring is required: checked after each row, every multi-leg entry would be unbalanced until its last posting. An error at commit rolls back the whole transaction, including the caller's business change: the ledger fails closed.

**Immutability (I2).** The service connects with a role that may only `SELECT` and `INSERT` on `entries` and `postings`, and `SELECT`, `INSERT` and `UPDATE` on `balances`, the only mutable table. Accounts are configuration: inserted, never updated. Only the migration role owns the tables, and the service never connects as it.

## 5. Posting and concurrency

### 5.1 Posting an entry

`LedgerApi.post` runs inside the caller's transaction, so that a settlement and its entry commit or roll back together (overview, section 7.2). It opens a savepoint first, so that an expected failure undoes only the ledger's own writes:

1. **Build the entry.** The caller passes an `EntryRequest`; the domain constructs an `Entry` and rejects it if it breaks I1 or I5. A broken request is a programming error and throws.
2. **Claim the source key.** `INSERT INTO entries ... ON CONFLICT (source_type, source_id, purpose) DO NOTHING RETURNING id`. A concurrent transaction with the same key waits for the first to finish.
   - If a row is returned, this is the first time: continue.
   - If none is, the entry exists: load it. If its postings are the same, return `AlreadyPosted` with its ID. If they differ, the caller reused a source key for another movement, a bug: throw.
3. **Check the accounts.** Load the accounts the postings reference; every one must exist and have the posting's currency.
4. **Update the balances** of the accounts that are not hot (section 5.2). If one would go negative and may not, roll back to the savepoint and return `InsufficientFunds` with that account. The caller's own work in the transaction is kept; the caller decides what to do.
5. **Insert the postings** in one batch.
6. Return `Posted` with the entry's ID. The deferred trigger checks I1 when the caller commits.

### 5.2 Balance updates

A balance is changed with one conditional statement, never by reading it, computing in Java and writing it back:

```sql
UPDATE ledger.balances
   SET balance = balance + :delta, version = version + 1, updated_at = now()
 WHERE account_id = :account_id
   AND (:allow_negative OR balance + :delta >= 0)
```

`:delta` is the sum of the entry's postings to that account, signed as in section 3.2, so each account is updated once per entry. PostgreSQL locks the row, re-reads its current value and evaluates the condition atomically: a concurrent update waits and then sees the new value. One row updated means the funds were there; zero rows means insufficient funds. There is no window in which two transactions both see the old balance, and nothing to retry.

**Lock order.** An entry updates its accounts' balances in ascending order of account ID. Two entries that touch the same accounts then lock them in the same order, so one waits for the other instead of each holding a lock the other needs (a deadlock). Callers follow one rule as well: lock their own rows, such as the charge, before calling the ledger.

### 5.3 Hot accounts

Some accounts take part in almost every entry: `platform:settlement` in every settlement and payout, `platform:fees` in every fee. If their balance rows were updated in every transaction, all postings would queue on those two row locks, and throughput would be one transaction at a time.

An account with `is_hot` set skips step 4: its balance row is not touched when an entry is posted. Instead:

- A scheduled job **folds** its postings into the balance row every minute: it adds the postings created between `folded_until` and a cutoff two minutes in the past, and moves `folded_until` to the cutoff, in one statement.
- Reading the balance of a hot account adds, to the folded balance, the postings created since `folded_until`. The result is exact, not an estimate.
- The two-minute lag is safe because a posting's `created_at` is its transaction's start time and every ledger transaction ends within 30 seconds (section 5.4): when the cutoff passes a time, no transaction that started before it can still commit.

A hot account cannot be guarded by the conditional update, so it must allow a negative balance (`check (not is_hot or allow_negative)`). The guarded accounts are the tenant and sub-account liabilities, which stay in-transaction; the platform accounts are the hot ones. A load test (k6) compares both modes and publishes the numbers.

### 5.4 Timeouts

The ledger role runs with `lock_timeout = 2s`, `statement_timeout = 5s` and `transaction_timeout = 30s` (PostgreSQL 17). A transaction stuck behind a lock fails quickly instead of piling up connections, and the 30-second bound is what makes hot-account folding exact. The values are a starting point, revised with load-test results.

## 6. API

Other modules use the ledger only through `LedgerApi` and the types it takes and returns, such as `AccountId`, all in the module's own package (`dev.finaxis.core.ledger`); everything else in the module is internal.

```java
public interface LedgerApi {
    AccountId openAccount(AccountRequest request);               // idempotent on (tenant, code)
    PostResult post(EntryRequest request);                      // idempotent on the source key
    Balance balanceOf(AccountId account);
    Page<PostingView> history(AccountId account, Cursor cursor, int limit);
}

sealed interface PostResult permits Posted, AlreadyPosted, InsufficientFunds {}
record Posted(EntryId entry) implements PostResult {}
record AlreadyPosted(EntryId entry) implements PostResult {}
record InsufficientFunds(AccountId account) implements PostResult {}
```

- `EntryRequest` carries the tenant, the source (type, ID, purpose), the effective date, the correlation ID, an optional reversed entry and the postings. An entry has at most 32 postings.
- `Balance` is the account, its balance as `Money` and the time it was read.
- `history` returns an account's postings, newest first, with keyset pagination on the posting ID: the cursor is the last ID returned, so pages stay fast however long the history grows. `limit` is at most 100.
- After an entry is posted, the module publishes `EntryPosted` (entry ID, tenant, source) in the same transaction, through Spring Modulith's event publication registry, once that registry exists (block G).

## 7. Verification

The **balance verifier** recomputes the ledger from its postings and compares (PR 1.13). It runs every 15 minutes, in one read-only `REPEATABLE READ` transaction, so every query sees the same snapshot:

| Check | Query |
|---|---|
| I1 | Every entry's debits equal its credits per currency, with at least two postings |
| I6 | Every balance equals the signed sum of its account's postings; for a hot account, the sum of those created before `folded_until` |
| I7 | Across all postings, debits equal credits per currency |

The verifier repairs nothing. A failed check increments `finaxis_ledger_invariant_violations_total{invariant}` and logs an error with the account or entry IDs only; an alert rule fires on any increase, and the runbook treats it as an incident. A full scan is acceptable at the project's volume; checking only what changed since the last run is the documented path for scale, together with monthly partitioning of `postings` (overview, section 19.3).

## 9. Trade-offs and alternatives

| Alternative | Why it was rejected |
|---|---|
| **Read, check and write the balance** (`SELECT ... FOR UPDATE`, compute in Java, `UPDATE`) | Correct, but holds the lock across a round trip to the application and splits one rule over two places. The conditional update checks and writes in one statement |
| **Optimistic locking** (compare `version`, retry on conflict) | Under contention most attempts fail and retry, so load multiplies exactly when an account is busiest. The conditional update waits instead and never retries |
| **No balance table**, sum the postings on every check | Always consistent, but the overdraft check must lock and sum the whole history, which grows forever. Used only for hot accounts, bounded by folding |
| **A holds table** beside the balances | A second source of truth that can drift from the postings. Holds as entries keep everything double-entry (overview, section 6.3) |
| **Signed amounts** instead of direction and positive amount | Hides the debit or credit nature of each leg and makes I5 a rule about absolute values. Direction plus a positive amount reads like an accounting journal |
| **Enforcement in Java only** | One bug, or one manual SQL statement, would corrupt the ledger silently. The database repeats every rule it can express |
| **A dedicated ledger database** (such as TigerBeetle) | Very fast and correct by design, but a second database to run, and settlement could no longer be one local transaction with the charge (overview, section 5.4) |
| **JPA (Hibernate) for persistence** | See [ADR 0004](../adr/0004-jdbc-client-in-the-ledger.md) |

## 10. Security considerations

The ledger has no network endpoint: its callers are other modules in the same process. The threats are a caller posting what it should not, someone with database access changing history, one tenant reading another's money, and load that blocks posting.

| STRIDE | Threat | Mitigation |
|---|---|---|
| **Spoofing** | A module posts an entry claiming a source fact it does not own, such as a fake settlement | Only modules call `LedgerApi`; each posts only for facts it has itself verified (settlement after the rails callback signature check). Every entry records its source and correlation ID, so any entry can be traced to the request that caused it |
| **Tampering** | Someone with database access edits or deletes postings to hide a movement | The service role cannot `UPDATE` or `DELETE` entries and postings, and a trigger rejects it for any role; the owner role is used only by migrations |
| **Tampering** | Someone edits a balance row directly | The verifier compares every balance with its postings and raises an alert (I6) |
| **Repudiation** | A tenant disputes that a movement happened | Entries are append-only and keep source, purpose, effective date, creation time and correlation ID; reversals link to the original. The tamper-evident audit trail (block G) adds who performed each action |
| **Information disclosure** | A tenant reads another tenant's accounts or postings | Every query filters by the tenant from the credential; Row-Level Security on `tenant_id` (block C) is the last barrier; another tenant's account returns `404`. Account codes and sources hold IDs only, no names, CPFs or Pix keys |
| **Denial of service** | Many postings queue on one balance row, or a slow transaction holds locks | Hot accounts skip in-transaction updates; lock, statement and transaction timeouts (section 5.4); at most 32 postings per entry; rate and amount limits per tenant before the ledger (overview, section 4.6) |
| **Elevation of privilege** | A caller makes an account overdraft-tolerant to spend money it does not have | Accounts are never updated; `allow_negative` is set only when an account is opened, by the code that opens it, and only the platform's own accounts use it |
